# Дополнение: поиск среди 5 млн камер

Ветка `feature/postgis-nearest-5m` развивает основное решение из `main`. HTTP-контракт и Legacy остаются прежними; поиск ближайших камер выполняется в PostgreSQL.

## Запуск

Нужны .NET 10 SDK, PowerShell и Docker с Linux-контейнерами. Из корня проекта:

```powershell
# Если БД другой ветки запущена, сначала остановите её:
docker compose down
git switch feature/postgis-nearest-5m
./Modern/database/setup-database.ps1 -Seed5Million
dotnet run --project Modern/CameraApi --launch-profile http
```

Без `-Seed5Million` скрипт создаст только схему и 6 начальных камер. С флагом добавит ещё 5 млн активных камер; повторный запуск пропустит seed. Начальные данные не удаляются: всего 5 000 006 строк, из них 5 000 005 активных.

Генерация идёт через `generate_series` в PostgreSQL. Координаты — сетка по всему миру, Id от -1 до -5000000 не затрагивают обычную последовательность. Вставка и отметка о её завершении сохраняются одной транзакцией. Нужны несколько минут и свободное место для данных, индекса и WAL.

Адреса прежние: API `localhost:5080`, БД `localhost:54329`, база `cameras`, пользователь и пароль `camera_demo`. Compose использует образ с PostGIS и отдельный том `camera-postgis-data`; том `camera-data` из `main` сохраняется. Перед обратным переключением ветки также выполните `docker compose down`.

Для локального PostgreSQL установите PostGIS, создайте БД и выполните:

```powershell
./Modern/database/setup-database.ps1 -Local -Port 5432 -Database cameras -Username camera_demo -Seed5Million
```

Пользователь должен иметь право включать PostGIS. Если `psql` отсутствует в PATH, передайте `-PsqlPath`. Для API задайте свою `ConnectionStrings__Cameras`, как в основном README.

## Что добавлено

- [SQL-миграция](database/002-postgis.sql) включает PostGIS, добавляет `location geography(Point,4326)` и GiST-индекс только для активных камер. Её можно повторно выполнить поверх исходной таблицы. Это обычный SQL-скрипт, не миграция EF Core.
- `location` автоматически вычисляется из longitude/latitude для старых и новых строк, в том числе при изменении координат.
- В EF Core подключён NetTopologySuite. Новый [GetNearestActiveAsync](CameraApi/Infrastructure/PostgresCameraRepository.cs) фильтрует, выбирает ближайшие камеры и считает расстояния в БД. В приложение приходит максимум limit строк.

В запросе есть важный нюанс: на проверенном PostgreSQL 16 общая сортировка по расстоянию и Id приводила к полному просмотру таблицы. Поэтому сначала KNN (`<->`) выбирает ближайших через индекс, включая равные расстояния на границе (`WITH TIES`), затем внешний запрос сортирует этот результат по расстоянию и Id и применяет limit. Если совпадений очень много, работы у второго этапа тоже будет больше.

Этот запрос написан параметризованным SQL через EF Core `Database.SqlQuery`. Расстояние считает `ST_Distance(..., false)` по сфере и переводит метры в километры. Исходный Haversine и его тесты сохранены, но API в этой ветке его не вызывает.

## Что проверено

Сборка и все 7 тестов проходят. На реальной БД проверены миграция существующих данных, HTTP-запрос, фильтрация активности, равные расстояния на границе limit и обновление location.

Замер в Docker с PostgreSQL 16.9 / PostGIS 3.5.2:

- 5 млн камер добавлены за ~97 секунд; таблица с индексами занимает ~1064 МБ.
- Повторный seed не добавил строк.
- Три запроса с limit 3, 100 и 10 использовали GiST и заняли ~0,27–1,16 мс SQL на прогретых данных.
- Прямая сортировка всей таблицы по расстоянию и Id с limit 3 заняла ~1,67 секунды.

Это одиночные замеры на синтетических данных. План можно проверить самостоятельно:

```powershell
Get-Content Modern/database/explain-nearest.sql -Raw | docker compose exec -T postgres `
  psql -U camera_demo -d cameras -v ON_ERROR_STOP=1
```

В плане ищем `Index Scan` по `idx_cameras_active_location`. Для рабочей большой БД потребовались бы отдельная проверка под нагрузкой и план миграции: добавление вычисляемой колонки переписывает таблицу, обычное создание индекса блокирует запись на время построения.
